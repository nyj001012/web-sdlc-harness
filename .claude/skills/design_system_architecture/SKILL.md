# Skill: System Architecture, Tech Stack & Data Flow Design

## Workflow (작업 순서)

1. **요구사항 및 현황 분석 (Context Analysis)**
   - 사용자의 프롬프트 요구사항을 분석하고, `Bash` 도구(`tree`, `ls`)와 `Read`로 현재 프로젝트의 디렉터리 구조·매니페스트·설정 파일을 파악한다.
   - 기존 스택이 이미 존재하면 그것을 SSOT 후보로 채택하고, 신규 프로젝트면 백지에서 선정한다.

2. **기술 스택 선정 (Tech Stack Selection)**
   - 요구사항에서 스택을 **역산**한다. 판단 축: 데이터 성격과 처리량, 실시간성 요구, 정합성/트랜잭션 요구, 배포 환경(클라우드/온프레미스/폐쇄망), 팀 역량, 운영 부담, 기존 자산.
   - 다음 계층을 **빠짐없이** 확정한다.
     - 언어 / 런타임 / 패키지 매니저
     - 프론트엔드 프레임워크 및 상태·데이터 페칭 전략
     - 백엔드 프레임워크 및 계층 구조(예: Controller / Service / Repository 등 계층 명칭 확정)
     - 데이터 저장소(및 필요 시 캐시·메시지 브로커·시계열 저장소 등 용도별 분리)
     - 테스트 도구(단위·컴포넌트·통합·E2E), 모킹 도구
     - 린트 / 포맷터 / 정적 타입 검사 도구(해당하는 경우)
     - 로깅·관측성 스택, 인프라·CI/CD·배포 방식
   - 🚨 **주의:** 특정 프레임워크를 기본값으로 가정하지 않는다. 각 선택에는 **선정 근거**와 **탈락한 대안 및 탈락 이유**를 반드시 함께 적는다.
   - 요구사항만으로 결정이 갈리는 항목은 지어내지 않고 사용자에게 질의한다.

3. **구조·경로·명령어 규격화 (Structure, Ownership & Commands)**
   - 확정한 스택의 관용 구조에 맞춰 디렉터리 레이아웃을 정의하고, **역할별 쓰기 소유권**(프론트엔드 / 백엔드 / 테스트(FE·BE·E2E) / 인프라 / 문서)을 경로 단위로 배정한다.
   - 하위 에이전트가 실행할 **표준 명령어**를 스택에 맞게 확정한다: 의존성 설치, 린트, 포맷, 정적 타입 검사, 단위 테스트(FE/BE 각각), E2E 테스트, 빌드, 실행.
   - **계약(Contract) 산출 형식**을 정한다: 정적 타입 언어면 타입/인터페이스 파일, 그 외에는 스키마 문서(OpenAPI, JSON Schema, protobuf 등) — 파일 확장자와 검증 명령까지 명시한다.
   - **아키텍처 규약**을 명시한다: 계층 분리 규칙, 트랜잭션 경계를 두는 계층, 로깅 컨텍스트 전달 방식(인자 드릴링 금지 대안), 실시간 통신 방식, 서버/클라이언트 상태 분리 전략, 리소스 정리(cleanup) 규칙.

4. **도메인 모델 경계 설계 (Domain Boundary Design)**
   - 핵심 엔티티와 그 관계, 각 엔티티가 어느 저장소에 놓이는지, 데이터 흐름(수집 ➔ 처리 ➔ 저장 ➔ 조회)을 정의한다.
   - 데이터 성격이 이질적이라면(예: 대량 이벤트/시계열 vs 관계형 마스터 데이터) 저장소를 용도별로 분리하고 그 근거를 남긴다.
   - 🚨 **경계 준수:** 컬럼 단위 스키마·인덱스·마이그레이션은 여기서 확정하지 않는다. 그것은 계약 설계와 구현 단계의 몫이다. 다만 성능상 반드시 지켜야 할 제약(파티셔닝 필요, 특정 조회 패턴 등)은 명시한다.

5. **관측성·보안·배포 제약 정의 (Constraints, not Implementation)**
   - 배포 환경(클라우드/온프레미스/폐쇄망), 로그 레벨 정책, 시크릿 관리 원칙, 최소 권한 원칙, 무중단 요구 여부 등 **DevOps가 벗어나면 안 되는 제약**만 항목으로 남긴다.
   - 컨테이너 구성, 설치 스크립트, CI/CD 파이프라인 상세는 DevOps Engineer에게 위임한다.

6. **산출물 교차 검증 및 적재 (Documentation & P2P Review)**
   - **자체 반론 검토:** 설계안의 취약점(특히 스택 선정 근거)을 스스로 열거하고, 각각에 대한 방어 근거 또는 감수하는 트레이드오프를 `design.md`에 남긴다. 반론을 세우지 못한 선택은 근거가 약한 선택이다.
   - `system-architect`는 서브 에이전트이므로 다른 아키텍트와 `SendMessage` 핑퐁을 돌릴 수 없다 (run_web_sdlc Rule 1).
   - 🚨 **자기완결성 요건:** 하위 에이전트는 이 파일을 **읽지 않는다.** 하네스가 `node .claude/tools/inject-design.mjs`로 전문을 각 에이전트의 시스템 프롬프트에 정적 주입한다. 따라서 "자세한 건 X 파일 참고"처럼 외부로 미루지 말고, 하위 팀이 필요로 하는 결정을 이 한 파일 안에서 끝낸다.
   - 최종 설계안을 `.claude/_workspace/01_architecture/design.md`에 저장한다. 아래 목차를 **필수**로 갖춘다.
     1. 요구사항 요약 및 제약
     2. **기술 스택** (계층 / 선택 / 버전 / 선정 근거 / 탈락 대안) — 표 형태 권장
     3. **디렉터리 구조 및 역할별 쓰기 소유권**
     4. **표준 명령어** (설치·린트·포맷·타입 검사·FE 테스트·BE 테스트·E2E·빌드·실행)
     5. **계약 산출 형식 및 검증 방법**
     6. **아키텍처 규약** (계층·트랜잭션·로깅·실시간·상태·정리 규칙)
     7. 도메인 모델 경계 및 데이터 흐름 (엔티티·관계·저장소 배치)
     8. 관측성·보안·배포 **제약** (상세 설계는 DevOps에게 위임)
     9. 미결 사항 / 후속 결정 필요 항목
   - 2·3·4번 항목이 비어 있으면 산출물을 완료로 간주하지 않는다. 하위 전원이 이 항목만 보고 움직이기 때문이다.

## Why (왜 이렇게 하는가?)

- **스택 종속 제거 (Stack Agnostic Harness):** 하네스가 특정 프레임워크를 전제하면 다른 프로젝트에 재사용할 수 없고, 요구사항에 맞지 않는 도구를 억지로 끼워 맞추게 된다. 스택 결정을 아키텍처 단계 한 곳으로 모아 프로젝트마다 유연하게 갈아끼우기 위함이다.
- **SSOT(Single Source of Truth) 제공:** 설계 공백이나 모호함으로 인해 하위 에이전트(PM, Tech Lead, 개발자, QA, DevOps)들이 각자 임의의 스택과 명령어를 창작(Hallucination)하는 것을 막고, 일관된 목표를 제공하기 위함이다.
- **병목 사전 차단 (Scalability):** 처리량·정합성·실시간성 요구를 초기 단계에서 스택 선택과 데이터 흐름에 반영해, 구현 이후에야 드러나는 I/O 병목과 구조 변경 비용을 방어하기 위함이다.
