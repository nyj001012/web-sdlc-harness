# Skill: Backend Black-box TDD Case Design


## Gate 2 — QA와 사용자 테스트 명세 확정 (테스트 코드 작성 전)
- **두 실행 모드:** CASE_REVIEW는 사용자 협업으로 명세만 작성한다. WRITE_TESTS는 승인된 명세를 읽고 Red 테스트 코드를 작성한다. 승인 전 기존의 테스트 작성/Red 알림 절차를 실행하지 않는다. 독립 호출도 유효한 승인이 없으면 CASE_REVIEW로 시작한다.
- **담당자:** 오케스트레이터가 FE/BE QA 중 협업 담당자 한 명을 지정한다. 담당자만 .claude/_workspace/04_test_cases/test-cases.md를 수정한다. 다른 QA는 경계 조건 제안을 담당자에게 배치 전달하고 사용자 질의·파일 덮어쓰기를 하지 않는다.
- **직접 입력:** 담당 QA가 먼저 사용자에게 "어떤 상황을 반드시 테스트했으면 좋겠나요?"라고 묻고 답변을 기다린다. "추가 요구 없음"도 명시적 답변이며 무응답으로 대체하지 않는다. 직접 사용자 채널이 없는 호스트에서는 전용 QA 사용자 세션에서 해당 TDD 스킬을 실행하고 확정 파일로 재개한다. 오케스트레이터의 Q&A 중계/누적 재스폰을 금지한다.
- **능동 추출:** 확정 시나리오/spec.md/requirements.md, 계약과 주입된 design_spec에서 정상·경계값·빈 입력·중복 요청·권한·타임아웃·실패 복구 등 작업에 맞는 누락 조건을 도출한다. 프로덕션 코드는 읽지 않는다.
- **Strict Batch:** 제안은 ID, 담당 레인(FE/BE), 조건/행동, 기대 결과, 추가 이유를 가진 번호 리스트로 한 번에 묶는다. "다음 테스트 케이스들을 추가해도 괜찮을까요? 번호별로 승인/제외/수정해 주세요"라고 일괄 질의한다. 한 케이스씩 순차 질문하지 않는다. 보완 질의도 남은 항목을 한 번에 묶으며 다른 QA가 중복 질문하지 않는다.
- **확정:** 사용자 필수 케이스와 승인된 추가 케이스만 명세에 포함한다. 제외 항목은 ID와 결정만 짧게 남긴다. 필수 계약 검증을 제외하는 요청과 계약이 충돌하면 [SPEC GAP]으로 멈추고 해결을 기다린다. 사용자 입력/배치 선택만으로 완성본 승인을 대체하지 않는다.
- **명세 형식:** 기준 요구사항·계약 경로, ID, 출처(사용자/QA), 레인, Given/When/Then 또는 입력·행동·기대 결과, 포함/제외 결정이 있어야 한다. 대화 원문·질의응답 요약을 파일에 넣지 않는다.
- **최종 사용자 승인:** .claude/_workspace/04_test_cases/test-cases.md 완성본을 보여주고 사용자 전용 터미널에서 `node .claude/tools/human-gate.mjs tests --approve`로 승인 입력을 받는다. 에이전트가 APPROVE를 생성/파이프 입력하지 않는다. 미응답·수정 요청 시 [WAITING USER]이며 코드 작성은 금지한다.
- **완료 조건(DoD):** 사용자 필수 상황 입력 → 경계 조건 배치 제안 → 사용자 선택 반영 → 완성본 명시적 승인 → tests --check 통과가 모두 필요하다. 보고는 [TEST CASES READY], 파일 경로·지문만 반환한다. 논의는 종료하고 테스트 작성자/개발자는 대화 상속 없는 새 컨텍스트에서 확정 파일만 참조한다.
- 테스트 명세·요구사항·시나리오·설계·계약 변경 시 재승인한다. 테스트 코드의 설명/이름에 케이스 ID를 대응시킨다. 승인 후 추가로 발견한 케이스도 다음 배치로 확인하고 명세를 갱신·재승인한다. 승인 범위 밖 테스트를 몰래 추가하지 않는다.

## Workflow (작업 순서)

- CASE_REVIEW는 위 사용자 검토 절차만 수행한다. 아래 코딩 단계는 tests --check 통과 후 WRITE_TESTS로 실행한다.

1. **테스트 스택 확인 (Stack Binding)**
   - 시스템 프롬프트 최상단에 **이미 주입된** `<design_spec>` 블록의 「기술 스택」·「소유권」·「표준 명령어」 섹션에서 백엔드 테스트 프레임워크, HTTP/통합 테스트 도구, 모킹 방식, 테스트 경로, 실행 명령을 확인한다.
   - 🚨 **주의:** `design.md`를 `Read` 등 어떤 도구로도 읽지 않는다. 전문이 이미 주입되어 있으며 중복 조회는 규약 위반이다.
   - 🚨 **주의:** 테스트 도구를 스스로 가정하지 않는다. 명시가 없으면 작성을 멈추고 `[SPEC GAP]`을 붙여 호출자에게 질의한다.

2. **계약 분석 및 클린 룸 준수 (Contract Review)**
   - `03_contracts/` 내의 타겟 계약만 확인한다.
   - 🚨 **주의:** 절대 실제 백엔드 구현 코드를 열어보지 않는다.

3. **백엔드 테스트 시나리오 기획 (BE Scenario Planning)**
   - 승인된 test-cases.md의 케이스 ID를 다음 카테고리에 대응시킨다. 미승인 추가 케이스는 배치 검토로 되돌린다:
     - **Happy Path:** 정상 상태 코드 및 계약에 맞는 응답 반환
     - **Edge Case:** 빈 결과, 경계값, 필수 파라미터 누락 시 클라이언트 오류 응답
     - **Failure Case:** 저장소 타임아웃, 트랜잭션 롤백, 하위 의존성 장애 시 서버 오류 응답 및 복구 동작

4. **모킹 적용 및 테스트 코드 작성 (Mocking & Implementation)**
   - 외부 의존성은 `<design_spec>`이 정한 모킹 방식으로 격리하여 독립적으로 실행 가능한 테스트를 짠다.
   - 코드를 소유권 표의 백엔드 테스트 경로에 스택 관용 네이밍으로 저장한다.
   - `Bash`로 표준 테스트 명령을 실행해 테스트가 문법 오류 없이 구동되고 **의도대로 실패(Red)** 하는지 확인한다.

5. **산출물 적재 및 알림 (Notify)**
   - `SendMessage`로 백엔드 담당 에이전트(`backend-developer`)에게 "실패하는(Red) 테스트 준비 완료"를 통보하여 구현을 유도한다.

## Why (왜 이렇게 하는가?)

- **확증 편향 방지:** 구현된 코드를 보고 테스트를 짜면 구멍(Bug)을 잡을 수 없다. 백엔드 QA는 오직 계약서만 보고 가혹한 장애 상황을 조성하여 백엔드의 에러 핸들링을 강제하기 위함이다.
- **스택 독립성:** 테스트 러너와 모킹 도구는 프로젝트마다 다르지만, "계약만 보고 실패 케이스부터 만든다"는 절차는 동일하다. 도구 선택을 아키텍처에 위임해 절차만 재사용하기 위함이다.
