# Skill: Backend API & Business Logic Implementation

## Workflow (작업 순서)

1. **스택 및 경계 확인 (Stack Binding)**
   - 시스템 프롬프트 최상단에 **이미 주입된** `<design_spec>` 블록의 「기술 스택」·「디렉터리 구조 및 소유권」·「표준 명령어」·「아키텍처 규약」 섹션을 확인한다.
   - 사용할 언어·프레임워크·데이터 접근 도구, 쓰기 허용 경로, 계층 명칭, 트랜잭션 경계 계층, 로깅 컨텍스트 전달 방식, 실행할 검증 명령을 여기서 확정한다.
   - 🚨 **주의:** `design.md`를 `Read` 등 어떤 도구로도 읽지 않는다. 전문이 이미 주입되어 있으며 중복 조회는 규약 위반이다.
   - 🚨 **주의:** 스택을 스스로 가정하거나 익숙한 프레임워크로 갈아타지 않는다. 정보가 없으면 구현을 멈추고 `[SPEC GAP]`을 붙여 호출자에게 질의한다.

2. **계약 및 테스트 명세 확인 (Contract & Test Review)**
   - `.claude/_workspace/03_contracts/`의 계약과 QA가 작성한 실패하는(Red) 테스트 코드를 읽고 목표를 파악한다.
   - 🚨 **주의:** 테스트가 실패한다고 해서 테스트 코드를 임의로 수정하는 행위는 절대 금지된다. 오직 프로덕션 코드로만 해결해야 한다.

3. **계층 분리 기반 로직 작성 (Layered Implementation)**
   - 단일 책임 원칙에 따라 `<design_spec>`이 정한 계층 구조대로 코드를 물리적으로 분리하여 작성한다. 일반적인 형태는 다음과 같으나, **명칭과 경로는 규약을 따른다.**
     - **요청 처리 계층:** 요청 파싱·검증 및 공통 에러 래퍼 적용
     - **비즈니스 로직 계층:** 핵심 도메인 규칙 수행
     - **데이터 접근 계층:** 순수 저장소 입출력

4. **트랜잭션 및 동시성 제어 (Transaction & Concurrency Control)**
   - 2개 이상의 쓰기 작업은 **반드시 `<design_spec>`이 지정한 계층(일반적으로 비즈니스 로직 계층)에서 하나의 트랜잭션으로 묶어 처리**한다. 데이터 접근 계층에서 트랜잭션을 열지 않는다.
   - 대용량 I/O 시 해당 런타임의 특성(스레드/이벤트 루프 모델)에 맞는 방식으로 처리하여 요청 처리 지연을 만들지 않는다.

5. **구조화 로깅 적용 (Structured Logging)**
   - 로거 객체를 함수 인자로 끝없이 넘기는 행위(Drilling)를 금지한다.
   - `<design_spec>`이 정한 요청 컨텍스트 전달 방식(요청 스코프 컨텍스트, DI 컨테이너, 미들웨어 바인딩 등)을 사용해 요청 식별자가 자동 포함된 구조화 로그를 남긴다. 정상 처리와 예외는 로그 레벨을 엄격히 구분한다.

6. **검증 통과 및 리뷰 요청 (Green & Request Review)**
   - `Bash` 도구로 `<design_spec>`의 표준 명령어(린트, 정적 타입 검사, 백엔드 테스트)를 실행해 모두 통과(Green)하는지 확인한다.
   - 성공 시 구현 완료 사실을 최종 보고에 담아 반환한다. 오케스트레이터가 이를 읽어 `code-reviewer`를 스폰해 코드 리뷰를 요청한다.

## Why (왜 이렇게 하는가?)

- **스택 종속 제거 (Portable Practice):** 계층 분리·트랜잭션 경계·구조화 로깅은 어떤 언어에서도 통하는 원칙이다. 프레임워크 이름을 하드코딩하지 않고 원칙만 강제하여 하네스를 어떤 프로젝트에도 재사용하기 위함이다.
- **클린 룸 TDD 보장 (Strict TDD):** 테스트 코드를 수정하지 못하게 강제함으로써, 개발자가 스펙을 자의적으로 해석하거나 꼼수를 부리는 것을 막고 QA가 의도한 엣지 케이스를 완벽히 방어하게 만들기 위함이다.
- **유지보수와 성능 극대화:** 계층 분리와 컨텍스트 기반 로깅으로 결합도를 낮추고, 런타임 특성을 무시한 I/O 처리로 서버가 병목에 걸리는 것을 방지하기 위함이다.
