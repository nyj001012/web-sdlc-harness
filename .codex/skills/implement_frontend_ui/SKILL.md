# Skill: Frontend UI & Client State Implementation

## Workflow (작업 순서)

1. **스택 및 경계 확인 (Stack Binding)**
   - 시스템 프롬프트 최상단에 **이미 주입된** `<design_spec>` 블록의 「기술 스택」·「디렉터리 구조 및 소유권」·「표준 명령어」·「아키텍처 규약」 섹션을 확인한다.
   - 사용할 프레임워크, 상태·데이터 페칭 전략, 실시간 통신 방식, 스타일링 방식, 쓰기 허용 경로, 실행할 검증 명령을 여기서 확정한다.
   - 🚨 **주의:** `design.md`를 `Read` 등 어떤 도구로도 읽지 않는다. 전문이 이미 주입되어 있으며 중복 조회는 규약 위반이다.
   - 🚨 **주의:** 스택을 스스로 가정하거나 익숙한 라이브러리를 임의로 추가하지 않는다. 정보가 없으면 구현을 멈추고 `[SPEC GAP]`을 붙여 호출자에게 질의한다.

2. **테스트 및 계약 분석 (Test & Contract Review)**
   - QA가 작성한 실패하는(Red) 프론트엔드 테스트와 `03_contracts/`의 계약을 읽고 요구되는 동작을 파악한다.
   - 🚨 **주의:** 테스트를 통과시키기 위해 테스트 코드를 수정하는 행위는 엄격히 금지된다.

3. **컴포넌트 설계 및 구현 (Component Implementation)**
   - `<design_spec>`의 렌더링 경계 규약(서버/클라이언트 렌더링 분리, 라우팅 구조 등)에 맞춰 컴포넌트를 소유 경로에 구현한다.
   - 재사용 단위(프레젠테이션 / 컨테이너 / 훅·스토어 등)를 규약에 맞게 분리한다.

4. **상태 및 리소스 관리 강제 (State & Resource Control)**
   - 서버 데이터는 `<design_spec>`이 정한 서버 상태 전략(캐싱·구독 계층)으로 다루고, 클라이언트 전역 상태에 불필요하게 복제하지 않는다.
   - 실시간 연결·타이머·이벤트 리스너·스트림을 여는 코드에는 **반드시 해제(cleanup) 로직을 짝지어** 작성하여 메모리 누수를 방지한다.

5. **관측성 및 예외 처리 (Observability & Error Isolation)**
   - 개별 요소마다 로깅을 하드코딩하지 않고, `<design_spec>`의 관측성 규약에 따라 **공통 이벤트 수집 계층**을 통해 사용자 상호작용을 기록한다.
   - 통신 실패에 대비해 주요 화면 단위에 오류 격리 및 폴백/로딩 UI를 적용한다.

6. **검증 통과 및 리뷰 요청 (Green & Peer Review)**
   - `Bash` 도구로 `<design_spec>`의 표준 명령어(린트, 정적 타입 검사, 프론트엔드 테스트)를 실행해 통과(Green)하는지 확인한다.
   - 성공 시 구현 완료 사실을 최종 보고에 담아 반환한다. 오케스트레이터가 이를 읽어 `code-reviewer`를 스폰해 리뷰를 요청한다.

## Why (왜 이렇게 하는가?)

- **스택 종속 제거 (Portable Practice):** 렌더링 경계 분리, 서버/클라이언트 상태 분리, 리소스 해제, 오류 격리는 프레임워크와 무관한 원칙이다. 원칙만 강제하여 어떤 프론트엔드 스택에도 하네스를 재사용하기 위함이다.
- **브라우저 뻗음(Freezing) 방지:** 실시간 데이터나 반복 타이머를 다룰 때 해제가 누락되면 즉각적인 메모리 누수가 발생한다. 이를 원천 차단하기 위함이다.
- **TDD 클린 룸 방어:** 개발자가 스펙을 자의적으로 변경하거나 테스트를 무력화하는 것을 막고, 오직 QA가 정의한 요구사항(DoD)만을 충실히 구현하게 강제하기 위함이다.
