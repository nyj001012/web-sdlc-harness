# Skill: Infrastructure, Runtime & CI/CD Pipeline Setup

## Workflow (작업 순서)

1. **제약 및 스택 확인 (Constraint Binding)**
   - 시스템 프롬프트 최상단에 **이미 주입된** `<design_spec>` 블록의 「기술 스택」(런타임·저장소·관측성)·「표준 명령어」·「관측성·보안·배포 제약」 섹션을 확인한다.
   - 🚨 **주의:** `design.md`를 `Read` 등 어떤 도구로도 읽지 않는다. 전문이 이미 주입되어 있으며 중복 조회는 규약 위반이다.
   - 배포 환경(클라우드/온프레미스/폐쇄망), 로그 정책, 권한 원칙, 무중단 요구를 확정한다.
   - 🚨 **주의:** 아키텍트가 제약만 남긴 영역의 **도구 선택과 상세 설계는 이 단계에서 확정**한다. 단, 제약을 벗어나는 선택은 금지하며 근거를 문서에 남긴다.

2. **실행 환경 구성 (Runtime Environment)**
   - 확정된 런타임·저장소에 맞는 실행 환경을 구성한다. (컨테이너 이미지·오케스트레이션 정의, 또는 호스트 직접 설치 구성)
   - 🚨 **주의:** 데이터 저장소의 영속성 구성은 성능·백업 관점에서 검증된 방식을 택한다. 임의 호스트 경로 직결처럼 I/O 병목이나 데이터 유실 위험이 있는 구성을 피하고, 선택 근거를 남긴다.
   - 애플리케이션 빌드는 `<design_spec>`의 표준 빌드 명령을 그대로 사용하고, 산출물 크기와 노출 범위를 최소화한다.

3. **설치·운영 스크립트 작성 (Provisioning Scripts)**
   - 배포 환경 제약(특히 네트워크 단절 환경이라면 사전 패키징 필요)을 반영하여 설치·실행·재시작·롤백 스크립트를 `.claude/_workspace/04_infrastructure/` 또는 인프라 소유 경로에 작성한다.
   - 🚨 **주의:** 프로세스 관리는 해당 OS·플랫폼의 **표준 방식**을 우선한다. 로그·설정 파일의 소유권과 접근 권한을 스크립트에 명시적으로 강제하고, 시크릿은 코드·이미지에 포함하지 않는다.

4. **CI/CD 파이프라인 구축 (Pipeline)**
   - 저장소 호스팅 플랫폼에 맞는 파이프라인 정의 파일을 작성한다. (플랫폼은 `git remote`로 판별하거나 `<design_spec>`의 명시를 따른다)
   - `<design_spec>`의 표준 명령어를 스테이지로 연결하고(설치 ➔ 린트/정적 검사 ➔ 테스트 ➔ 빌드 ➔ 배포), **테스트 스테이지가 완전히 통과한 이후에만 배포 스테이지가 실행되도록** 의존성을 엄격히 설정한다.
   - **하네스 정합성 스테이지:** 린트 단계에 `node .codex/tools/inject-design.mjs --check`를 추가한다. `design.md`가 갱신됐는데 에이전트 시스템 프롬프트에 재주입되지 않은 상태를 CI에서 실패로 잡는다.
   - 배포는 제약에 맞는 무중단 전략(롤링·블루그린·심볼릭 링크 교체 등)으로 구성한다.

5. **관측성 구성 (Observability)**
   - `<design_spec>`이 정한 로그 레벨 정책과 수집 경로에 맞춰 로그·메트릭 수집 구성을 작성한다. 폐쇄망 등 외부 전송이 불가한 환경이면 내부 수집 스택으로 구성한다.

6. **문법 검증 및 교차 검토 (Validation & Peer Review)**
   - `Bash` 도구로 작성된 설정·스크립트의 문법을 정적 검증한다. (설정 파서 검사, 파이프라인 린트, 셸 문법 검사 등)
   - 보안·성능 결함은 **자체 점검으로 확인한다.** 점검 항목과 결과, 판단이 갈린 지점을 최종 보고에 기재해 오케스트레이터가 판단할 수 있게 한다.
   - `devops-engineer`는 서브 에이전트이므로 다른 역할과 직접 통신할 수단이 없다 (run_web_sdlc Rule 1).

## Why (왜 이렇게 하는가?)

- **환경 제약 우선 (Constraints First):** 같은 애플리케이션도 클라우드와 폐쇄망에서 배포 방식이 완전히 달라진다. 인프라 도구를 하드코딩하지 않고 제약에서 역산하게 만들어 하네스를 어떤 환경에도 재사용하기 위함이다.
- **데이터 안정성과 성능 방어:** 저장소의 영속성 구성을 잘못 잡으면 부하 상황에서 병목과 유실로 직결된다. 검증된 구성만 채택하도록 강제하기 위함이다.
- **보수적인 보안 준수:** 고객 환경에 직접 설치되는 솔루션 특성상, 최소 권한 원칙과 플랫폼 표준 프로세스 관리를 사용하여 보안 감사(Audit)를 한 번에 통과하기 위함이다.
