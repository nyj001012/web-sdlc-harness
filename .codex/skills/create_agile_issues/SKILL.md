# Skill: Agile Task Breakdown & Feature Branch Creation

## Workflow (작업 순서)

1. **플랫폼 판별 및 범위 확정 (Context Analysis)**
   - `Bash` 도구로 `git remote -v`를 실행해 GitHub/GitLab 환경을 판별한다.
   - 🚨 **호출자(오케스트레이터/사용자)가 대상 파일과 변경 내용을 명시했다면 그것이 확정 범위다.** 이 경우 기획서를 근거로 범위를 넓히거나 대상을 바꾸지 말고, 받은 명세를 그대로 티켓 본문으로 옮긴다.
   - 확정 범위가 주어지지 않은 경우에만, 시스템 프롬프트 최상단에 **이미 주입된** `<design_spec>` 블록에서 1~2일 단위의 태스크와 DoD(완료 조건)를 도출한다.
   - 🚨 **주의:** `design.md`를 `Read` 등 어떤 도구로도 읽지 않는다. 전문이 이미 주입되어 있으며 중복 조회는 규약 위반이다.

2. **이슈(티켓) 생성 (Issue Creation)**
   - 티켓 발행 직전, 요청받은 대상 파일·변경 내용과 작성한 이슈 본문이 1:1로 일치하는지 대조한다. 불일치하면 생성하지 않고 호출자에게 질의한다.
   - 판별된 환경에 맞춰 `gh issue create` 또는 `glab issue create`를 실행하여 원격 저장소에 이슈를 등록한다.
   - 🚨 **중요:** 명령어 실행 후 터미널에 반환된 **'생성된 이슈 번호(예: #12)'**를 반드시 파악한다.

3. **작업 브랜치 파생 (Branch Switch)**
   - `git fetch`로 원격 기본 브랜치를 최신화한 뒤, 그 기준으로 파생한다. 이미 병합된 스테일 브랜치 위에서 분기하지 않는다.
   - `Bash` 도구를 사용하여 파악한 이슈 번호를 바탕으로 **`git switch -c feature/12-<슬러그>`** 명령어를 실행한다.
   - 브랜치명은 `<타입>/<이슈번호>-<슬러그>` 형식이며, 타입은 작업 성격에 따라 `feature`·`fix`·`chore`·`docs` 중에서 고른다.
   - `git branch --show-current`를 실행하여 현재 브랜치가 기본 브랜치(`main`)가 아닌 새 작업 브랜치로 정확히 이동되었는지 확인한다.

4. **산출물 적재 (Save Report)**
   - 생성된 이슈 목록과 현재 체크아웃된 브랜치명을 `.claude/_workspace/02_issues/issue_report.md`에 저장하고 종료한다.

## Why (왜 이렇게 하는가?)
- **메인 브랜치 오염 방지:** 이슈 PM이 사전에 브랜치를 따두지 않으면, 하위 에이전트들(FE/BE)이 `main` 브랜치에서 코드를 수정하는 대참사가 발생하기 때문이다. 격리된 환경(Clean Room)을 제공하는 것이 PM의 의무다.
