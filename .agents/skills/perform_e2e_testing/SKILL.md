# Skill: End-to-End Scenario Testing

## Workflow (작업 순서)

1. **E2E 스택 확인 (Stack Binding)**
   - 시스템 프롬프트 최상단에 **이미 주입된** `<design_spec>` 블록의 「기술 스택」·「소유권」·「표준 명령어」에서 E2E 프레임워크, 테스트 경로, 빌드·실행·E2E 명령을 확인한다.
   - 🚨 **주의:** `design.md`를 `Read` 등 어떤 도구로도 읽지 않는다. 전문이 이미 주입되어 있으며 중복 조회는 규약 위반이다.
   - 🚨 **주의:** E2E 도구를 스스로 가정하지 않는다. 명시가 없으면 작성을 멈추고 `[SPEC GAP]`을 붙여 호출자에게 질의한다.

2. **시나리오 및 DoD 분석 (Scenario Review)**
   - **주입된 `<scenario_spec>`(BA가 확정한 Gherkin)이 있으면 이를 시나리오의 1차 근거로 삼는다.** `Feature`/`Scenario`의 `Given`/`When`/`Then`을 그대로 E2E 테스트 케이스 단위로 옮기고, 이미 확정된 시나리오를 처음부터(from scratch) 다시 도출하지 않는다.
   - `.codex/_workspace/02_issues/` 하위의 완료된 이슈 명세서는 DoD·경계값 등 `<scenario_spec>`에 없는 세부사항을 보완하는 보조 근거로 쓴다. `<scenario_spec>`이 `[NOT READY]`면 이슈 명세와 완성된 화면만으로 폴백해 도출한다(기존 방식).
   - `<scenario_spec>`에 없는 시나리오가 필요하면 임의로 지어내지 말고 `[SCENARIO GAP: <필요한 항목>]`을 붙여 호출자에게 질의한다.
   - 🚨 **주의:** 내부 구현 코드를 훔쳐보고 테스트를 맞추려 하지 말고, 오직 '사용자의 관찰 가능한 행동과 결과' 관점에서만 시나리오를 기획한다.

3. **E2E 테스트 스크립트 작성 (Test Implementation)**
   - 소유권 표의 E2E 테스트 경로에 확정된 프레임워크 문법으로 테스트 코드를 작성한다.
   - 단순 응답 코드가 아니라, 화면에 보이는 텍스트·상태 변화·이동 결과 등 **사용자에게 드러나는 변화(Assertion)**를 깐깐하게 검증하도록 짠다.

4. **실행 환경 구성 및 구동 (Build & Run)**
   - `Bash` 도구로 `<design_spec>`의 표준 빌드 명령을 실행해 애플리케이션을 프로덕션에 준하는 모드로 준비한다.
   - 표준 실행 명령으로 애플리케이션을 띄우고(또는 E2E 프레임워크의 서버 자동 기동 설정을 활용), 표준 E2E 명령을 실행한다.

5. **에러 로그 트리아지 (Error Log Triage)**
   - **실패(Red) 시:** 즉시 작업을 멈추고 아래 **고정 형식**으로 판정을 반환한다. **절대 프로덕션 코드를 스스로 고치지 않는다.**
     ```
     [E2E FAILED]
     area: fe | be | data | infra | unknown
     failing: <실패한 시나리오명과 단정문 1줄>
     evidence: <로그 말미 최대 50줄 또는 요약. 전문 금지>
     repro: <재현 절차 3줄 이내>
     scope: <의심 경로 목록. 확실하지 않으면 비운다>
     artifacts: <스크린샷·트레이스 파일 경로>
     ```
   - **`area` 판정표:** `fe`(응답은 2xx인데 렌더링·상태·폴백이 기대와 다름) / `be`(4xx·5xx 또는 응답 스키마 불일치) / `data`(무결성 위반·컬럼 부재·마이그레이션 미적용) / `infra`(빌드·기동·포트·환경변수 문제로 테스트가 시작조차 못함) / `unknown`(단정 불가).
   - 🚨 **주의:** 로그 전문을 최종 보고에 싣지 않는다. `evidence`는 **말미 50줄 상한**이며 반복 스택 프레임과 무관한 경고는 지운다. 실패가 여러 건이면 각각 3줄로 요약하고 대표 1건만 상세히 적는다. 전문이 필요하면 파일 경로만 알린다.
   - 🚨 **주의:** `area`를 억지로 고르지 않는다. 근거가 없으면 `unknown`이다 — 잘못된 역할을 재스폰시키는 비용이 더 크다.
   - Phase 4 시점에는 다른 구현 역할이 모두 종료된 서브 에이전트이므로 직접 통신할 대상이 없다. 재스폰 대상은 오케스트레이터가 `area`를 보고 결정한다.
   - **성공(Green) 시:** 모든 시나리오가 통과하면 `[E2E TEST PASSED]`를 출력하고, 마스터 오케스트레이터에게 통제권을 넘겨 커밋을 진행하도록 유도한다.

## Why (왜 이렇게 하는가?)

- **진짜 유저 경험(UX) 검증:** 단위 테스트가 모두 통과했더라도, 실제 실행 환경에서는 레이아웃이 겹치거나 통신 정책(CORS 등)이 막힐 수 있다. 이를 릴리즈 직전에 완벽히 차단하기 위함이다.
- **로그 압축은 컨텍스트 방어다:** E2E 실패 덤프는 오케스트레이터 컨텍스트에서 가장 큰 우발적 소비자다. 전문을 흘리면 auto-compact가 앞당겨져 페이즈 인계 자체가 위태로워진다. 그래서 반환 시점에 자르는 것이 재스폰 이후에 요약하는 것보다 싸다.
- **구조화 판정이 조직도를 대체한다:** 실패를 어느 팀에 넘길지는 리더 노드가 있어야 결정되는 것이 아니다. `area` 한 필드로 재스폰 대상이 정해지므로, 계층을 늘리지 않고도 핀포인트 라우팅이 성립한다. 재스폰된 역할은 컨텍스트가 비어 있으므로 실제로 중요한 것은 압축된 판정의 정확성이다.
- **책임의 분리 (Separation of Concerns):** 테스터가 코드를 직접 고치게 두면 원칙이 무너진다. E2E 테스터는 오직 '발견'만 하고, 수정은 철저하게 구현 담당(FE/BE)이 책임지도록 강제하기 위함이다.
