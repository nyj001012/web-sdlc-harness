# Skill: Technical Wiki & API Documentation Generation

## Workflow (작업 순서)

1. **최신 컨텍스트 수집 (Context Gathering)**
   - 시스템 프롬프트 최상단에 **이미 주입된** `<design_spec>` 블록과, `Read`로 연 `.claude/_workspace/03_contracts/`의 계약 파일들을 대조해 시스템의 최신 스펙과 확정 기술 스택을 파악한다.
   - 🚨 **주의:** `design.md`를 `Read` 등 어떤 도구로도 읽지 않는다. 전문이 이미 주입되어 있으며 중복 조회는 규약 위반이다.
   - 매니페스트·설정 파일을 확인해 문서에 기재할 **실제 스택과 버전**을 확정한다. (기획 당시 표기와 다르면 실제 설치본을 기준으로 정정)

2. **API 및 데이터 명세서 작성 (API Specification)**
   - 계약 파일들을 분석하여 클라이언트 개발자가 즉시 참고할 수 있는 형태의 **[API 명세서]**를 마크다운으로 작성한다.
   - 🚨 **주의:** 엔드포인트, 메서드, 요청 파라미터, 응답 스키마, 발생 가능한 에러 코드를 누락 없이 테이블 형태로 구조화한다. 실시간 채널을 사용하는 경우 메시지 스키마와 연결 수명주기도 포함한다.

3. **아키텍처 및 의사결정 요약 (Architecture Guide)**
   - `<design_spec>`을 바탕으로 신규 합류자가 시스템을 이해할 수 있도록 **[시스템 아키텍처 개요 및 주요 의사결정(ADR)]** 문서를 작성한다.
   - **기술 스택 선정 근거와 탈락한 대안**을 반드시 포함한다. (예: "왜 이 저장소를 선택했는가", "왜 이 통신 방식인가", "리소스 해제·로깅 규약이 왜 필요한가")

4. **운영 가이드 작성 (Operations Guide)**
   - `<design_spec>`의 표준 명령어를 기준으로 로컬 실행·테스트·빌드 절차와 대표적인 트러블슈팅 항목을 정리한다.

5. **산출물 적재 및 종료 (Save & Terminate)**
   - 작성된 문서들을 `docs/wiki/` 하위에 용도별로 나누어 저장한다. (예: `docs/wiki/api_spec.md`, `docs/wiki/architecture.md`, `docs/wiki/operations.md`)
   - 🚨 **주의:** 저장이 완료되면 `[위키 문서화 완료]` 메시지를 출력하고 우아하게 종료한다.

## Why (왜 이렇게 하는가?)

- **버스 팩터(Bus Factor) 방어:** 핵심 개발자가 이탈하거나 팀이 교체되더라도, 시스템 구조와 API 스펙이 항상 최신 문서로 남아 프로젝트의 영속성을 보장하기 위함이다.
- **스택 결정의 보존:** 기술 스택은 프로젝트마다 달라지므로, "무엇을 왜 골랐고 무엇을 버렸는지"가 문서에 남지 않으면 다음 사람이 같은 고민을 반복한다. 선정 근거를 자산으로 남기기 위함이다.
- **문서화 부채 해결:** 코드는 바뀌었는데 문서는 과거 버전에 머물러 혼선을 빚는 상황을 막기 위해, 릴리즈·문서화 단계에서 동기화를 기계적으로 강제하기 위함이다.
